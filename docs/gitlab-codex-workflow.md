# 내부 GitLab 환경에서 Claude Code + Codex 운영 가이드

이 문서는 내부 GitLab 저장소를 사용하는 팀이 `Claude Code`와 `Codex`를 함께 사용할 때, 코드 리뷰와 테스트 실행을 어떻게 운영하면 좋은지 정리한 가이드입니다.

## 목적

- `Claude Code`는 구현 중심으로 사용합니다.
- `Codex`는 리뷰, 테스트 실행, 회귀 점검 중심으로 사용합니다.
- 최종 품질 게이트는 GitLab CI로 유지합니다.

핵심은 역할 분리입니다. 구현과 검증을 분리하면, 같은 변경사항을 다른 관점에서 다시 확인할 수 있어서 버그와 테스트 누락을 더 잘 잡을 수 있습니다.

## 권장 역할 분담

### Claude Code

- 기능 구현
- 리팩터링
- 초안 테스트 코드 작성
- 반복적인 코드 수정

### Codex

- 변경사항 코드 리뷰
- 테스트, 린트, 타입체크 실행
- 실패 원인 분석
- 위험한 변경 포인트 식별
- 테스트 누락 지적

## 내부 GitLab 기준 권장 흐름

### 1. 기능 브랜치에서 구현

개발자는 기능 브랜치에서 `Claude Code`로 구현을 진행합니다.

예시:

```bash
git checkout -b feature/add-streaming-fix
```

구현이 어느 정도 끝나면, 커밋 전 또는 MR 생성 전에 `Codex`에게 리뷰와 테스트를 맡깁니다.

### 2. Codex로 로컬 점검

`Codex`에게 아래와 같이 요청합니다.

```text
현재 변경사항 코드 리뷰해줘. 버그, 회귀 가능성, 테스트 누락 위주로 봐줘.
```

```text
테스트를 실행하고 실패 원인을 분석해줘. 필요하면 최소 수정안까지 제안해줘.
```

```text
git diff 기준으로 위험한 변경만 추려서 리뷰해줘.
```

이 단계에서 `Codex`는 보통 다음을 수행하게 됩니다.

- 변경 파일 확인
- diff 검토
- 관련 코드와 테스트 파일 확인
- 테스트/린트/타입체크 실행
- 문제 요약 및 수정 제안

### 3. 내부 GitLab에 Merge Request 생성

로컬 점검이 끝나면 내부 GitLab에 MR을 생성합니다.

이때 `Codex`는 MR 설명 작성을 돕는 용도로도 사용할 수 있습니다.

예시:

```text
현재 변경사항 기준으로 GitLab MR 설명 초안을 작성해줘.
배경, 변경 내용, 테스트 결과, 리뷰 포인트를 포함해줘.
```

### 4. GitLab CI로 최종 검증

로컬에서 `Codex`가 빠르게 1차 점검을 하고, 내부 GitLab CI가 최종 게이트 역할을 맡습니다.

권장 원칙:

- 로컬 `Codex` 결과만 믿고 머지하지 않습니다.
- 최종 판단은 GitLab CI 통과 여부로 합니다.
- CI 실패 시 `Codex`에게 실패 로그 분석을 맡깁니다.

예시:

```text
GitLab CI 실패 원인을 분석해줘. 이 로그 기준으로 가장 가능성이 높은 원인을 정리해줘.
```

## 내부 GitLab에서 특히 중요한 운영 포인트

### 1. 저장소 접근 방식 정리

내부 GitLab은 보안 정책 때문에 외부 SaaS보다 접근 제약이 있을 수 있습니다. 따라서 `Codex`가 직접 GitLab API를 호출하는 방식보다, 먼저 로컬 저장소 기반으로 운영하는 것이 안정적입니다.

권장 순서:

1. 로컬 체크아웃 저장소에서 리뷰와 테스트를 수행
2. 필요할 때만 GitLab MR 정보나 CI 로그를 별도로 전달
3. GitLab API 연동은 보안 승인 이후에만 검토

즉, 처음부터 GitLab 연동 자동화를 하려 하기보다, 로컬 git 작업 복제본 기준으로 검증 체계를 먼저 만드는 편이 현실적입니다.

### 2. 리뷰 기준을 팀 공통으로 고정

내부 GitLab에서는 리뷰 품질 편차를 줄이는 것이 중요합니다. 따라서 `Codex`에 매번 같은 리뷰 기준을 주는 것이 좋습니다.

권장 기준:

- 기능적 버그
- 예외 처리 누락
- 성능 회귀
- 테스트 누락
- 타입 불일치
- 기존 패턴 위반
- 보안상 위험한 처리

예시 프롬프트:

```text
이 브랜치 변경사항을 리뷰해줘.
다음 기준만 봐줘:
- 기능적 버그
- 예외 처리 누락
- 성능 회귀
- 테스트 누락
- 타입/인터페이스 불일치
- 보안상 위험한 코드
중요한 문제만 severity 순으로 정리해줘.
```

### 3. 실행 명령을 표준화

`Codex`가 잘 동작하려면 저장소마다 테스트 명령이 제각각이면 안 됩니다. 내부 GitLab 프로젝트라면 아래 명령을 repo 단위로 통일하는 것을 권장합니다.

예시:

```bash
pytest
ruff check src tests
ruff format --check src tests
bandit -r src
```

더 좋은 방식은 단일 진입점을 두는 것입니다.

예시:

```bash
make test
make check
make review
```

또는

```bash
just test
just review
```

이렇게 해두면 `Codex`에게 단순하게 요청할 수 있습니다.

```text
make review 실행하고 실패 원인을 분석해줘.
```

### 4. CI와 로컬 명령을 최대한 일치

내부 GitLab CI와 로컬 검증 명령이 다르면 혼선이 생깁니다. 가능하면 아래 원칙을 지키는 것이 좋습니다.

- 로컬에서 실행하는 `make review`와 CI job 내용을 최대한 동일하게 맞춤
- 테스트, 린트, 타입체크 순서를 로컬과 CI에서 동일하게 유지
- CI 전용 예외 규칙을 최소화

이렇게 해야 `Codex`가 로컬에서 찾은 문제와 GitLab CI 결과가 크게 어긋나지 않습니다.

## GitLab CI 연계 권장 구조

예시 `.gitlab-ci.yml` 구조:

```yaml
stages:
  - lint
  - test
  - security

ruff-check:
  stage: lint
  script:
    - ruff check src tests

pytest:
  stage: test
  script:
    - pytest

bandit:
  stage: security
  script:
    - bandit -r src
```

여기에 맞춰 로컬에서도 같은 명령을 `Codex`가 실행하도록 맞추면 됩니다.

## 추천 문서화 항목

내부 GitLab 프로젝트라면 아래 항목을 `README` 또는 `docs/`에 명시하는 것이 좋습니다.

- 표준 테스트 명령
- 표준 리뷰 명령
- MR 생성 전 최소 확인 항목
- GitLab CI 실패 시 확인 순서
- `Claude Code`와 `Codex`의 역할 분담

## 팀 운영 예시

### 예시 1. 구현 후 로컬 리뷰

1. 개발자가 `Claude Code`로 기능 구현
2. `Codex`로 diff 리뷰
3. `Codex`로 테스트/린트 실행
4. 문제 수정
5. GitLab MR 생성
6. GitLab CI 통과 후 머지

### 예시 2. CI 실패 분석

1. GitLab CI 실패
2. 실패 로그를 복사하거나 로컬에서 동일 명령 재현
3. `Codex`에게 실패 원인 분석 요청
4. 최소 수정안 반영 후 재실행

## 바로 사용할 수 있는 요청 예시

```text
현재 브랜치 변경사항을 리뷰해줘. 내부 GitLab MR 올리기 전에 버그와 테스트 누락만 집중해서 봐줘.
```

```text
pytest와 ruff check를 실행하고, 실패하면 원인을 요약해줘.
```

```text
이 변경사항 기준으로 GitLab MR 설명 초안을 작성해줘.
```

```text
GitLab CI 로그 기준으로 실패 원인을 분석해줘. 추정이 아니라 재현 가능한 원인 후보 위주로 정리해줘.
```

## 권장 결론

내부 GitLab 환경에서는 `Codex`를 GitLab에 직접 깊게 붙이기보다, 먼저 로컬 저장소 기준의 리뷰/테스트 실행 도구로 운영하는 것이 가장 현실적입니다.

정리하면 다음 원칙이 좋습니다.

- 구현은 `Claude Code`
- 검증은 `Codex`
- 최종 게이트는 GitLab CI
- 테스트 명령은 repo 단위로 표준화
- MR 전 로컬 리뷰와 테스트를 습관화

이 방식이면 내부망 제약이 있어도 운영이 쉽고, 팀 단위로도 바로 확장할 수 있습니다.
